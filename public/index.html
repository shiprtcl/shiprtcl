Upstream APIs drift.
Your ingestion heals.

SHIPRTCL — the Self-Healing Ingestion Protocol — fingerprints the structure of the third-party data you ingest — webhooks, API responses, partner file drops — maps it to your contract with a declarative rule, and repairs renamed, nested and retyped fields once. It never repairs them per request, and it never lets a model see your data.

How it works

Drift is rare. Traffic is constant. So do the hard part once.

An integration sees millions of payloads in a handful of distinct structures. SHIPRTCL recognizes the structure on every request for the price of a hash, and only works out how to map it the first time it is seen.

  1. 01

    Fingerprint

    Normalize JSON, form, CSV or XML into one tree. Discard every value. Hash the sorted (path, type) pairs.

  2. 02

    Resolve

    Known fingerprint? Use its rule. Unknown? Absorb it into an existing rule if that is provably safe, or synthesize a new one, once.

  3. 03

    Apply & validate

    Run the declarative rule. Validate the output against your contract on every request, fast path included.

  4. 04

    Release or quarantine

    Valid output is delivered and re-signed. Anything else is held or quarantined, encrypted, never delivered half-formed.

The resolution ladder

Cheapest, safest answer first. The model is the last resort.

hit

The fingerprint already has a rule. This is where the overwhelming majority of traffic lands.

~0.2 ms · no I/O
absorb

Added fields, omitted optionals, new nulls: an existing rule still applies, and SHIPRTCL can show it. The new fingerprint is aliased, and a rename is never mistaken for an absence.

sub-ms · no new rule
match

A deterministic matcher maps event_type→event, buyer.email_addr→customer.email and qty→quantity from names and types alone, with a confidence score.

sub-ms · once per shape
model

Optional. Any OpenAI-compatible endpoint (Workers AI, Ollama, vLLM). It sees a redacted skeleton of paths and types, and its output is checked against both structures.

~1 call per new shape
human

Low-confidence and model-assisted rules wait in shadow. You approve, reject or edit. Every rule carries its provenance.

policy-driven
Scope

Not just webhooks. Every direction third-party data flows.

The engine maps any payload to any contract. How the payload travels decides which runtime rules apply, and v0.1 doesn't specify all of them yet. Here is exactly where each case stands.

v0.1

Inbound, pushed to you — webhooks, partner POSTs, CSV and form drops. The spec, engine and reference proxy all cover it today.

spec §10 · proxy
SEP-0001

Inbound, you fetch it — your app calls a vendor API and the response shape drifts. The engine already translates responses as a library. A gateway mode with synchronous misses and fail-closed errors is proposed.

read the proposal →
SEP-0002

Outbound, you write to them — your payload is stable, but the vendor's accepted schema changes. That is contract drift: detected from schema diffs and rejections, repaired by re-mapping, and never auto-activated for writes.

read the proposal →
Designed to be distrusted

Self-healing that leaves a receipt.

“Self-healing” doesn't mean your pipeline silently changes behaviour. It means a fix is proposed, checked, applied only when policy allows it, and recorded as a CloudEvent.

∅

Values never leave

Fingerprints are built from key paths and types. Map-like objects keyed by ids or emails collapse to MAP, and data-like key names are redacted before any model call.

≠

Models can't write values

Synthesizers may only emit to, from, cast and each, over paths that exist on both sides. Prompt injection through key names is bounded to a wrong-but-valid mapping.

⊘

Fail closed

Every output is validated against your contract, on every request. If it doesn't validate, it isn't delivered.

✓

Signatures survive

Upstream signatures (GitHub, Stripe, HMAC) are verified on the raw body. Translated payloads are re-signed with Standard Webhooks.

Run it locally

git clone https://github.com/shiprtcl/shiprtcl.git && cd shiprtcl
npm install && npm run all     # build, vectors, 37 tests, site

# fingerprint any payload
echo '{"a":1,"b":{"c":"x"}}' | node packages/shiprtcl/dist/cli.js fingerprint

# start the reference proxy
node packages/shiprtcl/dist/cli.js serve shiprtcl.config.json

Use the engine

// npm i shiprtcl
import { Engine } from 'shiprtcl';

const engine = new Engine({ contracts: [{ id: 'payments.v1', schema }] });
const r = await engine.process('payments.v1', { body, contentType });

r.status      // 'translated' | 'held' | 'quarantined'
r.resolution  // 'hit' | 'absorbed' | 'synthesized'
r.output      // valid against your contract, or undefined
r.events      // CloudEvents audit trail, value-free
Known limitations

What SHIPRTCL does not do — yet, or ever.

We'd rather you read these here than find them in production. The full list is in the whitepaper, §10.

All limitations →
  • Semantic drift is invisible to structure. Dollars→cents with the same type won't change the fingerprint. Use enum/minimum/maximum to catch it.
  • Valid isn't the same as correct. Two same-typed fields can be swapped and still validate. That's why there's confidence, shadow mode and review.
  • The matcher speaks English. Other naming conventions fall through to the model or to a human.
  • XML and YAML are specified, not yet implemented. The reference implementation covers JSON, form bodies and CSV/TSV today.
  • Outbound calls aren't covered yet. When a vendor changes what it accepts, that's contract drift, specified in SEP-0002. The gateway mode for fetched responses is SEP-0001.
  • The reference proxy is single-node. It demonstrates the runtime rules. It isn't a production gateway yet.
